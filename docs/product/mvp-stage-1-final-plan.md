# 同城搭子网站 MVP 第一阶段最终范围

## 文档状态

- 阶段：BATCH-P1 产品范围和页面结构定稿
- 性质：产品规划文档，不写代码
- 项目名称：同城搭子网站
- 首批城市：惠州、广州、深圳、上海
- 首批分类：饭搭子、运动搭子、学习搭子、出游搭子、K 歌搭子、摩友搭子、钓友搭子
- 约束：城市字段必须保留可扩展，不在产品或数据设计里写死限制

## MVP 目标

第一阶段 MVP 只解决一个核心问题：让本地用户能快速看到同城搭子需求，并能用低成本方式发布一个待审核的搭子草稿。

本阶段不追求完整社交闭环，不做强登录、个人主页、举报、私信、通知、支付或运营后台。重点是把范围、页面、字段、分工、批次和验收口径定清楚，为后续 BATCH-P2 到 BATCH-P5 分批实施提供边界。

## 用户角色

- 访客：可以浏览搭子列表、查看基础信息、按城市和分类理解需求。
- 发布用户：可以填写搭子需求，先进入本地草稿或待审核流程。
- 审核/运营角色：本阶段只定义概念，不实现后台、不实现真实审核系统。
- 登录用户：后续阶段再引入，本阶段不强制登录。

## 必做范围

- 明确首批城市和首批分类。
- 明确网站第一阶段页面清单和页面职责。
- 明确搭子需求的字段清单，包括展示字段、提交字段、状态字段和后续扩展字段。
- 明确本地草稿 / 待审核流程，不直接进入真实数据库发布。
- 明确多 Agent 分工和交付边界。
- 明确 BATCH-P1 到后续批次的执行建议。
- 明确 BATCH-P1 允许修改和禁止修改范围。
- 明确 BATCH-P1 验收标准。

## 暂不做范围

- 不强制登录。
- 不做真实登录、账号体系和个人主页。
- 不做举报、拉黑、内容安全审核后台。
- 不做站内私信、消息通知、飞书批量群发。
- 不做支付、会员、订单或商业化功能。
- 不修改数据库结构、RLS、Supabase 表或 SQL。
- 不处理生产部署、生产环境变量或联系方式安全策略。
- 不修改首页 `/`、搭子列表 `/partners`、发布页 `/post` 的现有页面代码。

## 核心流程

1. 用户进入首页，理解同城搭子平台定位和可选分类。
2. 用户进入搭子列表，按城市、分类和基础信息浏览需求。
3. 用户进入发布页，填写城市、分类、标题、时间、地点、人数、说明和联系方式等信息。
4. 发布结果先进入本地草稿或待审核状态，不直接公开为真实线上数据。
5. 后续批次在老板单独批准后，再实现数据库、审核、登录和联系方式安全策略。

## 首批城市策略

首批运营城市为惠州、广州、深圳、上海。产品文档和后续字段设计只把它们作为初始选项，不把城市字段限制为固定枚举。后续可以扩展到更多城市、商圈、行政区或地理位置字段。

## 首批分类策略

首批分类为：

- 饭搭子
- 运动搭子
- 学习搭子
- 出游搭子
- K 歌搭子
- 摩友搭子
- 钓友搭子

分类可以先作为前端选项和展示标签。后续如接入数据库，应保留 `category` 或 `category_key` 的扩展能力，避免只适配首批分类。

## 本阶段结论

BATCH-P1 只完成产品范围和页面结构定稿。任何 UI 实现、业务页面改动、数据库改动、SQL 执行、环境变量修改、部署或后续批次开发，都必须等待老板单独批准。
