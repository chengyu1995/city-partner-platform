# 同城搭子网站 MVP 第一阶段页面信息架构

## 文档状态

- 阶段：BATCH-P2
- 性质：信息架构文档，不写 UI 代码
- 项目名称：同城搭子网站
- 适用页面：首页 `/`、搭子列表页 `/partners`、发布搭子页 `/post`
- 首批城市：惠州、广州、深圳、上海
- 首批分类：饭搭子、运动搭子、学习搭子、出游搭子、K 歌搭子、摩友搭子、钓友搭子

## 信息架构原则

- 先让用户确认“这是同城找搭子的地方”，再给城市、分类和发布入口。
- 移动端优先展示决策信息：城市、分类、时间、地点、人数、状态。
- 首页负责理解和分流，列表页负责筛选和浏览，发布页负责低门槛收集需求。
- MVP 第一阶段不强制登录，访客可以浏览，发布先进入本地草稿 / 待审核流程。
- 不在文案或结构中承诺实时公开、即时匹配、站内私信或平台担保。

## 全站信息层级

| 层级 | 信息 | 目的 |
| --- | --- | --- |
| L1 | 同城搭子平台定位 | 让用户立即理解网站用途 |
| L2 | 城市和分类 | 帮用户快速判断是否有相关入口 |
| L3 | 搭子需求摘要 | 让用户看到真实使用场景和信息密度 |
| L4 | 发布入口 | 引导用户提交自己的需求 |
| L5 | 状态与风险提示 | 降低用户误解，说明草稿 / 待审核边界 |

## 首页信息架构

首页目标：让访客在 5 秒内理解平台定位，并选择浏览或发布。

### 信息顺序

1. 平台定位：同城找饭搭子、运动搭子、学习搭子、出游搭子等。
2. 主行动入口：浏览搭子、发布搭子。
3. 城市入口：惠州、广州、深圳、上海。
4. 分类入口：饭搭子、运动搭子、学习搭子、出游搭子、K 歌搭子、摩友搭子、钓友搭子。
5. 最新 / 推荐搭子预览：标题、城市、分类、时间、地点、人数。
6. 发布流程提示：发布后先保存为本地草稿或进入待审核。

### 首页模块职责

| 模块 | 必要信息 | 不应承载的信息 |
| --- | --- | --- |
| 首屏定位 | 平台名称、用途、浏览和发布入口 | 复杂规则、长段安全说明 |
| 城市入口 | 首批 4 个城市，可提示后续扩展 | 固定死城市范围的表达 |
| 分类入口 | 首批 7 个分类 | 分类运营规则或后台配置 |
| 搭子预览 | 少量摘要信息 | 完整详情、联系方式 |
| 发布提示 | 草稿 / 待审核流程 | 真实审核后台承诺 |

## 搭子列表页信息架构

列表页目标：让访客按城市和分类快速筛选，判断是否有值得查看或响应的搭子需求。

### 信息顺序

1. 页面标题和轻说明：正在找同城搭子。
2. 城市筛选：惠州、广州、深圳、上海，保留扩展入口或不限城市概念。
3. 分类筛选：首批 7 类。
4. 列表结果摘要：当前筛选条件、结果数量或状态。
5. 搭子卡片列表。
6. 空状态 / 错误状态 / 加载状态。
7. 发布入口：当前没有合适内容时引导去发布。

### 搭子卡片信息层级

| 优先级 | 字段 | 展示目的 |
| --- | --- | --- |
| P0 | 标题 | 判断需求主题 |
| P0 | 城市、分类 | 判断是否相关 |
| P0 | 时间、地点 | 判断能否参与 |
| P1 | 期望人数、已有状态 | 判断参与门槛和热度 |
| P1 | 状态 | 区分草稿、待审核、已发布等概念 |
| P2 | 简短说明 | 补充活动内容和要求 |
| P3 | 标签、预算、注意事项 | 后续扩展，不应挤占移动端首屏 |

## 发布搭子页信息架构

发布页目标：低门槛收集一条可审核的搭子需求，避免用户误以为提交后会立即公开。

### 信息顺序

1. 发布说明：填写后先保存为本地草稿或进入待审核。
2. 城市和分类：先确认需求归属。
3. 标题：一句话说明想找什么搭子。
4. 时间、地点、人数：决定可参与性。
5. 需求说明：活动内容、适合人群、注意事项。
6. 昵称和联系方式：本阶段只作为草稿 / 待审核字段。
7. 提交结果：保存草稿、提交待审核、校验失败或保存失败。

### 表单分组

| 分组 | 字段 | 说明 |
| --- | --- | --- |
| 基础归类 | 城市、分类 | 首批选项作为默认入口，不限制后续扩展 |
| 活动摘要 | 标题、时间、地点、期望人数 | 列表页必须能直接消费 |
| 详细说明 | 需求说明、适合人群、预算说明、注意事项 | 支撑详情或审核判断 |
| 联系信息 | 发布人昵称、联系方式类型、联系方式内容 | 暂不设计公开策略 |
| 状态反馈 | 草稿、待审核、失败、成功 | 明确提交后的去向 |

## 不进入本批的信息架构

- 不设计登录页、个人主页、私信页、举报页或运营审核页。
- 不设计数据库 schema、RLS、审核后台或联系方式安全策略。
- 不修改 `/`、`/partners`、`/post` 的页面代码。
- 不进入 BATCH-P3 到 BATCH-P5 的 UI 实现、数据接入或部署工作。

## BATCH-P3 建议

- 基于本文档实现首页、搭子列表页、发布页的静态 UI 信息层级。
- 优先保证 375px 下标题、筛选、卡片和发布表单字段顺序正确。
- 页面代码实现前应再次确认不接真实数据库、不强制登录、不公开联系方式。
