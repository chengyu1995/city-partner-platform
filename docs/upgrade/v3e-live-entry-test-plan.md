# 3E-LIVE-FIX 手工测试计划

## 测试边界

- 不执行 SQL。
- 不修改 `.env`。
- 不部署。
- 不手工创建或修改 `hermes_jobs`。
- 只通过飞书线上入口观察回复和后续状态。

## 用例 1：网站首页需求必须进入项目总管确认

发送：

```text
新需求：做同城搭子网站首页
```

预期飞书回复：

```text
【项目总管确认】
我理解你的需求：
我的建议：
我建议先这样做：
关键问题：
请回复：批准建议 / 选 A / 选 B / 补充要求
```

验收点：

- 回复必须是项目总管确认消息。
- 不新增 `request_text = 做同城搭子网站首页` 或 `新需求：做同城搭子网站首页` 的 `hermes_jobs queued` 执行任务。
- 不直接进入 `workflow_stage = execution`。
- 不回复普通“已收到任务”。

## 用例 2：批准建议后才进入任务树草案

在用例 1 收到项目总管确认后，回复：

```text
批准建议
```

预期：

- 飞书回复 `【项目总管：任务树草案】`。
- 只记录任务树草案到 `hermes_messages`。
- 不新增普通网站执行类 `hermes_jobs queued`。

## 用例 3：批准任务树后才进入待分发清单

在收到任务树草案后，回复：

```text
批准任务树
```

预期：

- 飞书回复 `【项目总管：待分发任务清单】`。
- 只记录待分发清单到 `hermes_messages`。
- 不新增普通网站执行类 `hermes_jobs queued`。

## 用例 4：批准分发第 1 批后才允许写 BATCH-01

在收到待分发清单后，回复：

```text
批准分发第 1 批
```

预期：

- 飞书回复 `【项目总管：第 1 批已分发】`。
- 只允许新增 BATCH-01 产品规划任务。
- 新增任务应是产品规划文档任务，不是 UI、前端、后端、测试、部署任务。

## 用例 5：系统升级需求仍走升级任务逻辑

发送：

```text
新需求：执行系统升级阶段 3F
```

预期：

- 不进入 `【项目总管确认】` 网站产品流程。
- 仍可按原系统升级任务逻辑创建 queued 任务。
- 不创建 BATCH-01 产品规划任务。

## 回归检查

- `新需求: 做同城搭子网站首页` 使用英文冒号时，也应进入 `website_product_request`。
- 重复发送网站首页需求时，即使历史上存在错误 queued 任务，也应优先进入项目总管确认，而不是 duplicate 入队提示。
- 系统升级类文本只要包含 `系统升级`，仍应被分类为 `system_upgrade_request`。
